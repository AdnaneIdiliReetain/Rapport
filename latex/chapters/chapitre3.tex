\subsection{Transformation de Données avec SystemFieldMapping}

Le cœur de l'architecture d'intégration repose sur le mécanisme de configuration \texttt{SystemFieldMapping}, permettant de définir des règles de mappage métadonnées entre les systèmes externes et Salesforce. Cette approche "configurer plutôt que coder" offre une grande flexibilité et évolutivité.

\noindent Le système de transformation des données s'appuie sur un moteur configurable qui traite les payloads JSON provenant des systèmes sources selon des règles définies dans les métadonnées. Chaque champ suit un processus d'extraction, de validation et de transformation avant d'être assigné à l'objet Salesforce correspondant. Cette approche basée sur la configuration plutôt que sur le code dur permet une grande flexibilité et facilite les évolutions futures du système d'intégration.

\noindent Suite à ce tableau, voici les différents types de logique de transformation utilisés :

\begin{itemize}
  \item \textbf{Direct Mapping} : Transfert direct de la valeur source vers le champ cible sans modification.
  \item \textbf{Convert to Lowercase} : Conversion des adresses email en minuscules pour assurer l'uniformité et faciliter la déduplication.
  \item \textbf{DateIso} : Extraction de la partie date d'une chaîne au format ISO et conversion en objet Date Salesforce.
  \item \textbf{CegidStatusLogic} : Logique conditionnelle complexe qui détermine le statut de la commande en fonction des quantités (positives="paid", négatives="returned", mixtes="partially refunded").
  \item \textbf{Concatenate} : Fusion de plusieurs valeurs sources avec un séparateur pour créer une valeur composite dans le champ cible.
\end{itemize}

Ces transformations permettent d'adapter les données brutes reçues des systèmes externes au modèle de données Salesforce tout en appliquant les règles métier nécessaires.

\subsection{Mécanisme de Déduplication}

\begin{mdframed}[style=breakablegreen]
La déduplication des profils clients est un enjeu critique pour le RCU. Le système utilise la classe \texttt{AccountTriggerHandler} pour détecter et fusionner les doublons selon l'algorithme suivant:

\begin{itemize}
    \item Détection primaire basée sur l'email (correspondance exacte)
    \item Détection secondaire sur le numéro de téléphone normalisé
    \item Analyse de similarité des noms/prénoms en cas d'ambiguïté
    \item Système de scoring avec seuil minimal de 85\% pour fusion automatique
    \item Validation manuelle pour les scores entre 70\% et 85\%
    \item Journalisation complète des fusions dans l'objet \texttt{MergeAudit\_\_c}
\end{itemize}

L'extrait de code ci-dessous illustre la logique de détection des doublons:
\end{mdframed}

\begin{lstlisting}[language=Java, caption=Extrait de AccountTriggerHandler.cls]
private List<Account> findPotentialDuplicates(Account newAccount) {
    String email = newAccount.Email;
    String phone = newAccount.Phone;
    String normalizedPhone = normalizePhoneNumber(phone);
    
    List<Account> potentialDuplicates = new List<Account>();
    
    if (String.isNotBlank(email)) {
        potentialDuplicates.addAll([
            SELECT Id, FirstName, LastName, Email, Phone
            FROM Account
            WHERE Email = :email
            AND Id != :newAccount.Id
        ]);
    }
    
    if (String.isNotBlank(normalizedPhone)) {
        potentialDuplicates.addAll([
            SELECT Id, FirstName, LastName, Email, Phone
            FROM Account
            WHERE Phone = :normalizedPhone
            AND Id != :newAccount.Id
            AND Email != :email
        ]);
    }
    
    return potentialDuplicates;
}
\end{lstlisting}

Une fois les doublons potentiels identifiés, le système applique une logique de fusion élaborée qui respecte les règles de priorité des sources tout en préservant l'intégrité des données. Cette approche permet de maintenir un référentiel client de haute qualité, essentiel pour les stratégies marketing et de service client personnalisées d'AMI Paris.

\subsection{Défis Rencontrés et Solutions}

\begin{mdframed}[style=breakablegreen]
Plusieurs défis techniques ont été surmontés durant l'implémentation du RCU:

\begin{itemize}
    \item \textbf{Normalisation des données}: Développement d'algorithmes spécifiques pour standardiser les formats d'adresse, téléphone et nom en tenant compte des spécificités régionales (Europe, Asie, Amériques)
    
    \item \textbf{Gestion des homonymes}: Implémentation d'un système de détection avancé utilisant la distance d'adresse et l'historique d'achat pour différencier les véritables homonymes
    
    \item \textbf{Limitations Salesforce}: Optimisation des requêtes SOQL pour respecter les limites de gouvernance, notamment lors des processus de fusion à grande échelle
    
    \item \textbf{Performance du système}: Introduction d'une architecture de traitement par lots asynchrones pour les opérations volumineuses de synchronisation et fusion
    
    \item \textbf{Complexité des règles métier}: Modélisation des règles d'assignation SA/Store dans un moteur de règles configurable pour faciliter l'évolution des besoins
\end{itemize}
\end{mdframed}
